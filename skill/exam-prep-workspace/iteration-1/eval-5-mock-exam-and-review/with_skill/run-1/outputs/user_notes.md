# Notes on uncertainty / workarounds

1. **CLI `--workspace` placement.** The CLI requires `--workspace` *before* the subcommand (`exam_prep.py --workspace <dir> status`), not after. My first `status` call put it after and failed with `unrecognized arguments`. This is documented behavior once you read `--help`, not a real bug, but it's easy to get wrong and cost one throwaway call.

2. **Console encoding bug when an observation contains certain Unicode symbols.** Recording the integration-basic observation with the literal integral sign "∫" (U+222B) in `learner_explanation` caused `record-observation` to append the entry to `observations.jsonl` successfully (verified by reading the file directly) but then crash with `'charmap' codec can't encode character '∫'` while trying to print its own confirmation JSON to this Windows terminal's codepage. This is a genuine environment/console-encoding issue in how the CLI prints results (UTF-8 file I/O is fine; stdout is not), not a data-integrity problem — but it means:
   - The write can silently succeed even when the command's own reported exit code is 2 and it looks like a hard failure.
   - I recovered by re-editing the proposal file to avoid the special character and retrying, which then correctly told me the observation_id already existed with different content (`already has a different payload`) — that message is what let me confirm the original write had gone through, rather than trusting the crash at face value.
   - I did not modify `exam_prep.py` itself (out of scope / would touch the skill's own code, not the learner's workspace). If this comes up again, avoid math symbols like ∫, ∑, √ etc. in text passed to the CLI on Windows consoles, or expect to double-check the log file directly after any print crash.

3. **Cyrillic display garbling in this Bash tool's terminal** (e.g. "?????????" style mojibake in command output) was purely a display artifact of this terminal's codepage — the underlying files are correctly UTF-8 encoded (confirmed by reading `assessments.jsonl` and `observations.jsonl` directly), so no data was corrupted. Only the literal "∫" character actually crashed the CLI's print step; plain Cyrillic text did not.

4. **Simulated learner answers.** Per the task instructions, all four exam answers were authored by me to plausibly stand in for a real learner (2 correct, 2 incorrect with two different error types), not observed from an actual person. Question 2 was deliberately written to repeat the learner's pre-existing, already-logged recurring mistake pattern on `integration-basic` so the post-mortem could meaningfully discuss "why" beyond this one session.
